# CodeFlow 上下文阈值消融：面试报告

## 实验结论

目前不能用这次运行回答“80% 是否最优”。真实运行生成了 3 条预实验和 12 条正式阶段 trial 记录，但完整设计要求 108 条正式记录。实验器初版把序列化请求估算上限设得过低，多个请求在发送前被预算守卫拦截并超时；修正后再次运行被自动审批拒绝，因为会把私有仓库代码、工具输出和任务数据发送给 DeepSeek。没有将模拟数值补进来，也没有把不完整数据包装成正式结果。

## 面试问题

### 为什么 50% 可能过于保守？

当上下文使用率到 50% 就开始结构化 Compact，理论上会比 80% 更频繁地重写历史摘要，可能增加摘要模型输入/输出 Token、额外模型往返和总耗时，也可能在尚有充足窗口时重复压缩。这是需要验证的机制假设。本次不完整运行里，50% 组在 4 条正式阶段记录中出现 1 次 Compact；80% 和 93% 各为 0 次。不过四条记录没有覆盖完整任务，且多次 Provider 请求被挡住，不能据此推导 50% 一定更贵或更慢。

### 为什么 93% 可能存在风险？

治理触发点靠近窗口末端，留给工具结果增长、Token 估算误差和下一轮生成的余量较小，可能造成突发 Compact、上下文超限或紧急裁剪，也更容易让关键早期约束在来不及治理前被挤出。这是设计上的风险来源，不是本次实验已测出的失败因果。当前部分样本没有测出有效的超预算差异，不能声称 93% 已造成溢出。

### 80% 哪些指标更好，哪些没有优势？

目前没有能支持“80% 更好”的有效指标。部分正式运行里，80% 的已记录总 Token 为 26,177，低于 50% 的 44,524 和 93% 的 33,493；按样本差异计算，分别少 41.2% 和 21.8%。但 80% 组 4 条记录全部为 `task_timeout`，其中多次是 Provider 预算守卫拒绝请求；低 Token 和较短时延很可能反映请求没有完成，而不是更有效的上下文治理。对应的 verifier 记录通过率 75% 也与 4/4 超时状态冲突，不能作为质量结果。

93% 组在部分样本有 2/4 任务状态 passed，50% 组为 1/4，80% 为 0/4；样本量、任务覆盖和运行完整性都不足，不能据此宣称 93% 胜出。当前正式矩阵真正的结论是“无结论”。

### 实验数据支持什么？

- 实验确实改动了 CodeFlow 的 `structured_compact_threshold`，没有把它与 ContextAssembler 的工作预算比例或最终 Provider 窗口上限混为一谈。
- 第一次预实验在目标压力约 0.70 时，50% 触发 1 次 Compact；80% 和 93% 没有触发。这证明该参数会影响治理行为，但这三个任务都没有成功完成，不能证明哪种阈值带来更好的最终结果。
- 正式阶段仅落盘 12/108 条 trial 记录，实际只覆盖两个任务的部分重复；费用账本显示累计已结算 ¥0.1579536。
- 中断实验账本、Manifest、journal、逐 Trial 记录和源文件路径均保留在 `.codeflow/e/2189b500/`，原始样本整理在 `raw_results.csv`。

### 局限与下一步

当前没有全量实验结论。请求输入上限错误会让超时和 Token 统计失真；远程模型的实际版本标识为 `deepseek-flash`，与配置别名 `deepseek-v4-flash` 需在正式报告里同时注明；远程模型即使温度固定也有非确定性。重新运行前要先取得允许向该模型服务发送仓库和任务数据的审批，然后使用修正后的 42,000 输入 Token 上限、每请求一次尝试和 ¥40.32 费用硬上限。应在新运行标识下完整执行 108 次，保留所有异常，并通过 Verifier 与最终产物检查确认成功状态。当前没有目标分支更新或代码提交。

## 40–60 秒面试回答

“我没有预设 80% 一定最好，而是把 CodeFlow 的结构化 Compact 阈值单独配置，固定 8,192 Token 窗口、0.80 的上下文工作预算、模型、任务和工具，再比较 50%、80%、93%。预实验在约 70% 压力时验证了 50% 会触发 Compact，而 80% 和 93% 不触发，说明开关确实改变了治理行为。但正式矩阵只保存了 12 条记录，80% 组还有 4 次任务超时，原因涉及 Provider 请求估算上限，不是可用于质量比较的结果。现在只能说实验尚无结论，不能把 80% 说成最优。下一步要在获得数据外发审批后，用修正后的预算守卫完成 108 次配对运行，再根据 Token、成本、P95 和 Verifier 结果决定阈值。”
